# 真实 Skill 场景扫描结论

本文基于 `E` 盘真实 skill 语料的批量扫描结果，提炼 ProvLoom 在真实生态中的可解释结论与局限。原始扫描目录位于 `/mnt/e/log`，样本根目录为 `/mnt/e/dangerous_skills`。

## 扫描范围

- 扫描时间：`2026-04-19T11:49:49Z` 至 `2026-04-19T12:29:01Z`
- 样本根目录：`/mnt/e/dangerous_skills`
- 分析模式：`epg_with_filtering`
- LLM API：开启
- 扫描总量：663 个 skill root
- 完成情况：663 完成，0 skipped，0 failed

这些结果来自真实仓库中的 skill 定义，而不是仅来自仓库内合成 benchmark。样本同时包含：

- repo 根目录 skill
- `skills/` 子目录 skill
- `.claude/`、`.agents/`、`.cursor/` 等嵌入式 skill

从路径形态看，663 个样本中：

- 357 个来自 repo 根目录或其他非标准位置
- 283 个来自 `skills/` 目录
- 12 个来自 `.claude/`
- 8 个来自 `.agents/`
- 3 个来自 `.cursor/`

这说明真实生态中的 skill 形态非常分散，扫描器不能只假设单一目录结构。

## 总体结果

风险等级分布如下：

- `medium`: 605 / 663，约 91.3%
- `critical`: 47 / 663，约 7.1%
- `low`: 11 / 663，约 1.7%

风险分值呈现明显离散化，而不是连续分布：

- `0` 分：11 个
- `25` 分：605 个
- `100` 分：47 个

根因标签几乎被单一标签主导：

- `llm_decision_induced_action`: 655 个
- `unknown`: 6 个
- `prompt_injection_suspected`: 2 个

检测行为分布如下：

- `network_access`: 657 个
- `process_spawn`: 370 个
- `shell_execution`: 157 个
- `file_write`: 47 个

最常见行为组合为：

- 287 个：仅 `network_access`
- 209 个：`network_access + process_spawn`
- 114 个：`network_access + process_spawn + shell_execution`
- 43 个：`file_write + network_access + process_spawn + shell_execution`

## 面向真实 Skill 场景的核心结论

### 1. 真实 skill 生态里，“联网”几乎是默认背景行为，不能单独作为恶意判据

657/663 个样本命中了 `network_access`，占比约 99.1%。这说明在真实 skill 场景中，联网是常态而不是例外，原因通常包括：

- skill 自身就是外部服务集成器
- skill 在执行时依赖模型 API
- skill 读取在线文档、SaaS、搜索或第三方平台

进一步看，610 个样本同时满足以下条件：

- 命中 `network_access`
- `primary_chain` 为空
- 存在 LLM 事件

其中 287 个样本甚至只有 `network_access` 这一项行为命中。对真实 skill 来说，这类结果更像“环境联网”或“能力联网”的存在性证明，而不是有足够证据支持的数据外流结论。

结论是：在真实 skill 语料中，`network_access` 更适合作为风险入口信号，而不适合作为独立定罪条件。

### 2. 真正有高置信度安全价值的，是少数带有完整源到汇链路的样本

663 个结果中，只有 47 个样本带有非空 `primary_chain`，占比约 7.1%。这 47 个样本与 `critical` 风险完全重合，说明当前系统真正“站得住脚”的高风险结论，主要来自可恢复的解释链，而不是来自粗粒度行为命中。

这些链条的共同特征非常鲜明：

- source 主要是敏感本地文件
- relay 多为 `Run Command` 或 `Read File`
- sink 全部收敛为 `unknown`

链路 source 分布：

- 29 个来自 `/etc/hosts`
- 14 个来自 `/etc/group`
- 3 个来自 `/etc/debian_version`
- 1 个来自 `/etc/apt/apt.conf.d/`

这意味着当前 `critical` 结论的可信来源，不是“它联网了”，而是“它读取了敏感系统文件，并且该读取与后续外发行为在图上可连通”。

结论是：对真实 skill 场景，ProvLoom 已经能把“普通联网 skill”和“出现敏感源文件读出链的 skill”区分开，但这个能力目前只覆盖少量样本。

### 3. 当前系统更擅长发现“敏感文件到外发”的显式链路，不擅长解释更常见的 SaaS/Agent 工作流

大量中风险样本的典型组合是：

- 仅联网
- 联网加子进程
- 联网加子进程加 shell

这在真实生态里非常常见，例如：

- 搜索、网页抓取、SaaS API 封装
- 构建、调试、脚手架、代码分析 skill
- 邮件、日历、文档、表格、社交平台接入 skill

这些 skill 可能确实有被滥用空间，但如果没有明确的敏感 source、明确的 payload relay、明确的 sink endpoint，就很难给出“恶意链路”级别的结论。当前结果中 616/663 的 `primary_chain` 为空，正说明系统对这类真实 workflow 的解释仍偏弱。

结论是：现阶段的解释能力偏向“显式数据外流检测”，而不是“真实 agent workflow 风险建模”。

### 4. 根因标签在真实场景中严重塌缩，区分度不足

655/663 个样本被标成 `llm_decision_induced_action`。这对 benchmark 可能够用，但对真实 skill 生态的分析价值有限，因为它把多种本应区分的风险模式都压成了一个桶：

- 合法 SaaS 调用
- 过度授权的工具使用
- shell 包装的网络访问
- 本地文件读取后上送
- 只是依赖 LLM API 的普通执行

结论是：在真实 skill 语料上，根因标签当前更像“调用了 LLM 驱动行为”的总括说明，而不是分析师可直接使用的归因结果。

### 5. 风险分数过于三段化，缺少真实场景需要的排序能力

真实语料中只有三个分数档位：0、25、100。这会带来两个直接问题：

- 605 个中风险样本全部堆在 25 分，无法区分“只是联网”与“联网加 shell”谁更值得优先审查
- 47 个严重样本全部堆在 100 分，无法区分“读取 `/etc/group`”与“读取更敏感的凭据类文件”的优先级

结论是：对于真实 skill 审计，当前风险分数更像等级映射，不像排序分数。

## 需要特别说明的偏差与噪声

### 1. 部分结果明显包含扫描框架本身引入的背景流量

扫描配置启用了 LLM API，并且 657 个样本出现了网络事件，657 个样本中又有 657 个命中 `network_access`。这强烈暗示：

- 真实 skill 行为与扫描框架联网行为还没有被完全解耦
- 只要执行过程里存在模型调用，联网行为就会被稳定记录

因此，在真实 skill 场景下，任何只依赖 `network_access` 的告警都应被视为“待进一步归因”的弱证据。

### 2. sink 统一为 `unknown`，削弱了外流结论的可操作性

47 条非空主链全部以 `unknown` 作为 sink。这意味着系统已经能确认“存在流出方向”，但还不能稳定恢复：

- 是模型 API
- 是第三方服务
- 是用户声明的目标站点
- 还是别的网络终点

对真实审计来说，`unknown` sink 会影响处置效率，因为分析师无法立刻判断是允许域名还是异常目的地。

### 3. 扫描完成不代表执行完全成功

虽然总体状态是 663 全部 `completed`，但 `stderr_preview` 里仍存在不少运行期异常：

- 76 个 `TimeoutError`
- 24 个命令拼接错误
- 10 个 `node: not found`
- 5 个 `SKILL.md not found`
- 5 个 `npm: not found`

这说明当前“completed”更接近“扫描任务完成并产出结果”，而不是“skill 被完整、成功执行”。在真实 skill 语料上，部分结果实际上是“部分执行 + 部分证据”。

## 如果只看更接近真实生产语料的样本

结果中有少量显式 eval/test 样本，例如：

- `skill-scanner/evals/...`
- `test_skills/malicious/...`
- `skill-vettr/test/fixtures/...`

如果把这类明显偏测试的路径粗略排除，仍有 646 个样本保留，分布变化不大：

- `medium`: 590
- `critical`: 45
- `low`: 11
- 非空主链：45

这说明前面的主结论并不是由少数 benchmark 样本“撑起来”的，而是对真实 skill 生态总体成立。

## 对论文或 benchmark 叙述最有价值的结论

如果需要把这批真实语料结果写进论文、报告或 benchmark 章节，最稳妥的表述应该是：

- 在真实 skill 生态中，联网、子进程和 shell 都非常常见，不能被直接等同于恶意。
- ProvLoom 的真正优势不在于“看见联网”，而在于当存在敏感本地源文件时，能够恢复出从 source 到 sink 的解释链。
- 当前系统在真实场景下的主要瓶颈，是对普通联网 workflow 的误报压缩、对 sink endpoint 的恢复，以及对根因标签的细化。
- 因此，真实 skill 评测应至少区分两层目标：行为筛查能力与高置信度链路恢复能力，不能只看总体告警率。

## 下一步建议

### 1. 将 `network_access` 拆成“模型背景联网”和“skill 自身联网”

最值得优先改动的是把 LLM API、框架默认网络请求、skill 明示的外部请求分开建模。否则真实语料下会天然出现大面积中风险堆积。

### 2. 把 `critical` 的判定门槛显式绑定到“敏感 source + 连通链”

从当前结果看，这样的判定最接近真实安全价值，也最容易让分析师信服。

### 3. 丰富 sink 解析

至少应区分：

- 模型 API 域名
- 用户声明 URL
- 第三方 SaaS 域名
- 原始 IP:port

这样真实场景中的处置价值会明显提升。

### 4. 让分数变成可排序的连续信号

建议将以下因素纳入分层加权：

- source 敏感度
- sink 可解释性
- 是否出现本地暂存文件
- 是否出现 shell 包装
- 是否存在多跳 relay
- 是否发生在声明能力之外

### 5. 将“执行失败但有部分证据”的样本单独标记

真实 skill 生态中依赖缺失很常见。应把“完整执行”和“部分执行”分开统计，避免把运行环境缺陷误写成安全结论。

## 一句话总结

基于 `/mnt/e/dangerous_skills` 的 663 个真实 skill 扫描结果，可以得到一个清晰判断：真实生态中“联网”是常态，ProvLoom 当前最可靠的价值在于发现少量带敏感源文件读出链的高风险 skill，而不是对大规模联网 skill 给出细粒度、低误报的安全归因；要把这套方法真正推广到真实 skill 场景，下一步必须优先解决背景联网去噪、sink 恢复和根因细化。
